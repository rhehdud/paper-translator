# 리소스 흐름에서 실행 가능한 테스트로: Petri-Net-가이드 LLM 테스트 생성 (From Resource Flow to Executable Tests: Petri-Net-Guided LLM Test Generation for Concurrent Stateful Rust APIs)

Kaiwen Zhang, Guanjun Liu, Tongji University, Shanghai, China, zhangkw@tongji.edu.cn

# 초록

동시 상태 기반 라이브러리 API는 진화하는 리소스 소유권, 수명 주기 상태, 그리고 경쟁적인 인터리빙을 통해 동작을 노출한다. 대형 언어 모델은 실행 가능한 Rust 테스트를 합성할 수 있지만, 그 출력은 종종 API 전제 조건을 위반하거나 얕게 남아 있거나 동시성을 우연히 순차 추적으로 축소한다. 반대로, 모델 기반 및 체계적인 테스트 기법은 의미론적 제어를 제공하지만, 추상 시나리오를 실행 가능한 테스트로 전환하기 위해 상당한 수작업 코드를 필요로 한다. 본 논문은 형식적 시나리오 설계와 저비용 테스트 구체화 사이의 격차를 해결한다.

우리는 동시 상태 기반 Rust API에 대한 테스트 생성을 위해 Petri-net-가이드 방법론을 제시한다. 이 방법은 API 리소스, 수명 주기 조건 및 인과적 의존성을 색상 토큰과 전환으로 표현한다; 법적 딥-스테이트, 근접-법적, 그리고 부분 순서 동시 시나리오를 도출한다; 그리고 이러한 시나리오를 LLM 기반 코드 합성을 위한 제약된 중간 표현으로 사용한다. 로컬-신뢰성 계약과 구조적 수리 루프는 구체화 과정에서 모델링된 의도를 보존한다, Petri-가이드 스케줄 형성은 체계적 탐색을 위해 고충돌 동시성 골격을 우선시한다. 계층화된 의미론적 오라클은 합성 실패와 대상 API의 예상 동작 위반을 구분한다.

우리는 Rust 동시성 라이브러리를 위한 프로토타입을 구현하고, 실행 가능성, 구조적 충실도, 딥-스테이트 도달성, 경계 실패 발생, 그리고 충돌 범위를 검사하는 평가 프로토콜을 정의한다. 핵심 방법론 원칙은 책임을 분리하는 것이다: Petri net은 의미론적 의도, 리소스 흐름, 도달성, 충돌, 그리고 버그 관련 변이를 지정하고, LLM은 라이브러리별 구문, 작업 스캐폴딩, 그리고 어설션을 구현한다. 이 설계는 형식적 리소스 흐름 모델이 LLM 생성 동시성 테스트를 보다 신뢰성 있고, 상태 기반이며, 진단적으로 유용하게 만들 수 있는지 연구할 수 있는 구체적 기반을 제공한다.

## 1 서론

많은 Rust 라이브러리 API는 고립된 함수 인터페이스가 아니다. 그들은 핸들, 퍼밋, 클로저, 버퍼된 상태, 그리고 작업 수준 상호작용 패턴을 노출하며, 이들의 동작은 이전 연산과 경쟁 스케줄에 따라 달라진다. 이 설정에서 Rust의 타입 시스템은 광범위한 메모리 오류를 제거하지만, 라이브러리가 상위 수준 프로토콜을 준수한다는 것을 증명하지는 않는다. 남아 있는 버그는 의미론적 결함이다: 오래된 권한이 여전히 수용되고, 닫기 연산이 잘못된 동작을 무효화하며, 버퍼된 값이 손실되거나, 특정 인터리빙이 딥 스테이트에 도달한 후에만 테스트가 정지한다.

이러한 API는 세 가지 상호 연관된 이유로 테스트하기 어렵습니다. 첫째, 흥미로운 동작은 강하게 상태 의존적입니다: 많은 실패 모드가 합법적인 접두어가 비트리비얼한 리소스 구성을 설정한 뒤에만 나타납니다. 둘째, 접두어 자체가 의미론적으로 규율되어야 합니다; 그렇지 않으면 이후 관측은 의미가 없게 됩니다. 테스트가 유효한 프로토콜 상태를 실행하지 않았기 때문입니다. 셋째, 동시성은 원시 길이보다 부분 순서 수준에서 중요합니다. 길이가 긴 시퀀스는 우연히 노출되어야 할 경쟁을 직렬화하면 유용하지 않습니다.

기존 접근법은 이 공간의 일부만을 다룹니다. 모델 기반 및 종속성 인식 테스트는 합법적인 상태, 리소스 흐름, 경계 조건을 설명할 수 있지만, 이러한 추상화를 실행 가능한 Rust 테스트로 변환하려면 여전히 상당한 수작업 스캐폴딩, 작업 조정, API별 어설션이 필요합니다. 직접 LLM 프롬프트를 사용하면 그 코딩 부담이 줄어들지만, 동시에 의미론적 책임을 모델로 다시 밀어넣습니다. 실제로 LLM은 이벤트를 발명하거나, 활성화 조건을 위반하거나, 예약된 기능과 새로운 기능을 혼동하거나, 어설션을 약화시키거나, 동시 동작을 편리한 순차 트레이스로 평탄화할 수 있습니다.

이 논문의 입장은 의도적으로 좁습니다. 우리는 LLM에게 동시성 의미론을 처음부터 발견하도록 요구하지 않으며, 모델링 노력을 없애겠다고 주장하지도 않습니다. 대신, 우리는 Petri-네트 모델을 사용해 리소스 다중성, 인과성, 충돌, 그리고 거의 합법적인 경계 사례를 인코딩하고, LLM은 모델이 생성한 시나리오를 실행 가능한 Rust 코드로 구현하도록만 사용합니다. 스케줄러는 여전히 런타임 인터리빙을 탐색하고, API별 불변성은 여전히 작성해야 합니다. 핵심은 책임을 분리하여 의미론적 의도를 LLM 밖에 두고, 코드 구현은 비용이 적게 만드는 것입니다.

이러한 트레이드오프는 동시성 상태를 가진 Rust API에 특히 잘 맞습니다. Petri-네트는 송신자, 수신자, 퍼밋, 용량, 버퍼링된 메시지, 관측 의무를 토큰으로 표현할 수 있으며, 테스트를 진단적으로 유용하게 만드는 정확한 충돌과 인과 의존성을 표현할 수 있습니다. 그 구조가 명시되면 LLM은 상대적으로 잘 할 수 있는 일을 수행합니다: 대상별 설정, 작업 생성, 어설션, 정리. 핵심 설계 규칙은 간단합니다: 모델이 의미를 쓰고, LLM이 코드를 씁니다.

이 설계의 비용도 명확합니다. SyncPetri는 수동으로 작성된 리소스 모델, 어댑터, 시나리오 불변성을 필요로 하며, 그 스케줄링 형성은 Loom과 같은 도구보다 하니스 선택을 개선하지만 내부 검색을 대체하지는 않습니다. 우리는 이러한 한계를 앞서 명시합니다. 왜냐하면 그것이 적절한 기여를 정의하기 때문입니다: 완전 자동 동시성 검증이 아니라, 일부 모델링 노력을 대가로 생성된 테스트에 대한 더 강력한 의미론적 제어를 제공하는 테스트 아키텍처입니다.

구체적으로, SyncPetri는 색상 Petri-네트에서 합법적인 깊은 상태 트레이스, 거의 합법적인 경계 프로브, 부분 순서 동시 시나리오를 합성하고, 제한된 프롬프트와 구조적 수리 루프를 통해 이를 구체화하며, 결과 실행을 계층화된 오라클로 판단합니다. 이 오라클은 구체화 실패와 의미론적 실패를 분리합니다. 결과는 리소스 프로토콜에 버그가 존재하는 동시성 Rust API를 위해 설계된 테스트 파이프라인입니다.

우리는 다섯 가지 기여를 합니다:

- 우리는 리소스를 운반하는 전이를 통한 Petri-net 지침 시나리오 합성을 통해 동시성 상태 기반 Rust API 테스트를 형식화한다.  
- 우리는 추상 Petri-net 단계와 구체적 Rust 실행을 연결하는 어댑터 스키마와 로컬 신뢰성(local‑faithfulness) 계약을 정의한다.  
- 우리는 합법적 도달성, 근접 합법적 경계 변이, 그리고 부분 순서 동시성을 통합하는 시나리오 표현을 정의한다.  
- 우리는 생성 실패와 의미적 실패를 구분하는 제약된 구체화 루프와 다층 오라클을 제시한다.  
- 우리는 Loom 호환 하네스에 대한 Petri-net 지침 스케줄 형성 방법을 제안하고, tokio::sync 스타일 API에서 전체 워크플로를 구현한다.

## 2 문제 설정 및 실행 예시 (Problem Setting and Running Example)

우리는 세 가지 기본 특성을 가진 API를 대상으로 한다: 1) 상태성(Statefulness): 연산의 결과나 유효성은 시스템의 내부 추상 자원 상태에 크게 의존한다. 2) 자원 민감성(Resource sensitivity): 연산은 핸들, 허가, 버퍼링된 데이터, 접근 토큰 등과 같은 역량을 직접 조작한다—소비, 생산, 분할, 병합, 무효화 등을 수행한다. 3) 동시성 노출(Concurrency exposure): 여러 개별 작업이나 핸들이 동시에 상호작용하므로, 서로 다른 실행 스케줄이 완전히 다른 관측 가능한 결과를 낼 수 있다.

이것은 Rust 라이브러리의 유용한 일부를 포괄한다. 예를 들어 tokio::sync에서는 mpsc 채널이 송신자, 수신자, 허가, 버퍼링, 종료를 노출하고, watch는 최신값 세마틱과 관측된 상태를, broadcast는 지연된 수신자와 재생 경계를, 그리고 Semaphore는 획득, 해제, 종료 동작을 노출한다 [9–12]. 이러한 API는 로컬에서 테스트하기에 충분히 작지만, 진정한 의미적 조율을 요구할 만큼 풍부하다. Table 1은 실행 중인 mpsc 예시를 위한 간결한 추상화를 보여준다.

따라서 연구 문제는 다음과 같다: Petri-net 모델의 Rust API에서 의미 있는 동시성 테스트 시나리오를 합성하고, LLM을 사용해 그 시나리오를 실행 가능한 Rust 코드로 구체화하며, 결과 실행이 의도된 API 세마틱을 보존하는지 위반하는지를 판단할 수 있는가?

### 2.1 버그 모델 (Bug Model)

우리는 Rust의 타입 시스템과 엄격한 메모리 안전 검사에서 벗어나는 의미적 결함을 대상으로 한다. 이러한 결함을 네 가지 핵심 범주로 분류한다:

- B<sub>pre</sub> (**전제조건 강제** (Precondition Enforcement)): 추상적 전제 조건이 위반되었음에도 불구하고 잘못된 성공을 보이는 연산 (예: 닫힌 채널에 전송).
- B<sub>state</sub> (**후상태 불일치** (Post-State Inconsistency)): 리소스 회계, 소유권 이전, 또는 정리 로직이 연산 실행 후 사양과 일치하지 않는다.
- B<sub>race</sub> (**경쟁 민감성** (Race Sensitivity)): 스케줄에 따라 달라지는 인터리빙이 고수준 프로토콜이 엄격히 금지하는 관측 시퀀스 또는 상태 변화를 드러낸다.
- B<sub>live</sub> (**실행성 및 차단** (Liveness and Blocking)): 구현이 영구 차단, 깨진 깨우기, 또는 종료 상태에 도달한 후 종료하지 못하는 문제를 겪는다.

tokio::sync API에 대해, 이러한 범주는 send-after-close 성공, 오래된 핸들 수락, 값 업데이트 후 알림 상실, 불일치한 허가 회계, 또는 종료 레이스가 종료되지 않는 등 구체적인 결함 형태와 대응한다. 이 버그 모델은 우리 시드된 변이 평가의 기준이 된다.

### <span id="page-1-1"></span>2.2 실행 예시 및 기본 문제점 (Running Example and Baseline Pitfalls)

우리는 capacity-one Tokio MPSC 채널을 사용하여 SyncPetri 워크플로우를 동기화한다. 설정은 수신기 $R_0$ , 용량을 예약하는 일반 송신기 $S_p$ , 그리고 경계 프로브 역할을 하는 독립 송신기 $S_b$ 를 포함한다.

핵심 의미적 불변성은 미묘한 비동기 계약을 포함한다: 수신기를 닫으면 새로운 일반 전송 연산을 즉시 거부해야 하지만, 닫기 이전에 성공적으로 획득한 기존의 Permit 또는 OwnedPermit는 여전히 유효하며 버퍼에 메시지를 커밋하도록 허용해야 한다 [10]. 이후 수신기는 최종 종료 전에 이 미결 메시지를 비워야 한다.

이 미묘한 수명 주기 계약은 여러 가지 그럴듯한 의미적 결함을 만든다: 구현은 닫기 시 미결 허가에 의해 지원되는 메시지를 잘못 삭제하거나, 유효한 허가 커밋을 거부하거나, 닫기 플래그와 허가 카운터 사이의 내부 비동기화로 인해 무한히 걸리게 할 수 있다.

전통적인 테스트 패러다임은 이 동작을 분리하는 데 어려움을 겪는다. 순수하게 무작위 동시성 퍼지기는 용량을 예약하고, 닫기와 커밋을 경쟁하며, 이후 잔여 드레인을 검증하는 정확한 인터리빙 시퀀스를 생성할 가능성이 매우 낮다. 반대로, 순수 프롬프트 전용 LLM은 두 가지 상반된 실패를 자주 겪는다: 동시 실행을 단순화된 순차 추적으로 압축해 레이스를 완전히 놓치거나, 엄격한 순차 규칙을 환각(예: 모든 연산이 닫기 이후 실패한다고 가정)으로 만들어 API의 실제 계약과 일치하지 않는 잘못된 테스트 어설션을 생성한다.

1단계: 리소스 모델 및 깊은 상태. 초기에는 추상 초기 마킹 <sup>0</sup>에 두 개의 활성 송신기 능력, 하나의 활성 수신기, 개방 채널 토큰, 하나의 용량 토큰이 포함된다. 첫 번째 모델링된 이벤트는 용량을 예약함으로써 깊은 상태를 명시적으로 목표로 한다:

$$e_1 = \text{reserveOwned}(S_p) \rightarrow P_0.$$

결과 마킹은 Permit(0, )와 Cap(, 0)을 포함하는 별도의 구성으로 네트워크를 이동시킨다. 이는 관심 있는 깊은 상태를 나타낸다: 채널은 일반 개방 송신기나 단순 버퍼 항목과 구별되는 미결, 고립된 전송 능력(0)을 보유한다. 핵심적으로 모델은 허가-커밋 전이에서 Open()를 요구하지 않고 <sup>0</sup>을 소비하도록 규정하며, 일반 전송은 여전히 Open()와 자유 용량 두 가지에 의존한다.

2단계: 시나리오. 이 마킹에서 SyncPetri는 = {1, …, 7}에 대한 부분 순서 그래프를 다음 라벨로 구축한다:

1 : reserveOwned( ) → 0, 2 : spawn(1, 0), 3 : permitSend(0,1), 4 : close(0), 5 : recv(0) → 1, 6 : trySend(,2), 7 : recvEnd(0).

Rather than fixing a rigid, linear trace, only necessary causal dependencies are captured in ≺:

$$e_1 \prec e_2 \prec e_3, \qquad e_1 \prec e_4,$$

$e_3 \prec e_5, \qquad e_4 \prec e_5 \prec e_6 \prec e_7.$

이벤트 <sup>3</sup>과 <sup>4</sup>는 인과적으로 독립적이지만 겹치는 리소스 필드를 놓고 경쟁하므로 명시적 레이스 쌍으로 표시됩니다: (3, 4) ∈ #. 이 부분 순서는 두 가지 유효한 인터리빙을 안전하게 캡슐화합니다: commit-before-close와 close-before-commit. 이벤트 <sup>6</sup>은 거의 합법적인 경계 탐사 역할을 합니다; 5 이후에 채널의 용량은 비어 있지만 상태는 여전히 닫혀 있어, <sup>6</sup>이 정확히 하나의 활성화 조건(Open())을 위반한다는 의미입니다. 예상되는 관측값은 집합값 허용 클래스(set-valued allowed classes)로 매핑됩니다:

$$\Phi_{e_3} = \{ \text{SendOk} \}, \qquad \Phi_{e_5} = \{ \text{Msg}(m_1) \}, \Phi_{e_6} = \{ \text{ClosedLike} \}, \qquad \Phi_{e_7} = \{ \text{End} \}.$$

3단계: 제약된 LLM 구체화. 구조적 그래프는 느슨한 텍스트 설명 대신 매우 제약된 데이터 프롬프트로 직렬화된다. 프롬프트는 명시적인 리소스 매핑, 엣지 종속성, 그리고 허용 가능한 결과 범위를 제공한다.

추상 이벤트와 실행 가능한 작업 사이의 격차를 해소하기 위해, 프레임워크는 충돌 관계에서 실행 스캐폴딩을 도출한다. (3, 4) ∈ # 가 활성 동시성 쌍이므로, 프롬프트는 명시적 준비, 해제, 완료 핸드쉐이크를 요구한다.

## 3 공식 모델 (Formal Model)

### 3.1 API 추상화 및 컬러드 페트리 네트 (API Abstraction and Colored Petri Net)

우리는 가벼운 API 추상화로 시작한다

$$A = (R, O, \Sigma, \Omega),$$

여기서 R은 리소스 종류 집합, O는 연산 이름 집합이며, $\Sigma$는 각 연산을 타입이 지정된 인수와 결과 클래스에 매핑하고, $\Omega$는 런타임 오라클에서 사용되는 관찰 클래스 집합이다.

API 추상화는 컬러드 페트리 네트로 컴파일된다

$$N_A = (P, T, F, \chi, \lambda, q, u, M_0).$$

여기서 P는 유한한 장소 집합, T는 유한한 전이 집합이며, $F\subseteq (P\times T)\cup (T\times P)$는 흐름 관계, $\chi$는 각 장소를 토큰 색상 도메인에 매핑하고, $\lambda:T\to O$는 전이를 API 또는 하니스 연산으로 라벨링하며, $g_t$는 각 전이에 대한 가드 조건, $u_t$는 각 전이에 대한 토큰 업데이트 함수, $M_0$는 초기 마킹이다.

$I_t(p)$와 $O_t(p)$는 전이 t가 장소 p에서 입력 및 출력 토큰 다중집합을 나타낸다. 전이는 마킹 M에서 다음 조건을 만족하면 활성화된다:

활성화됨

$$(M, t) \iff g_t(M) = \text{true } \land \forall p \in P, I_t(p) \subseteq M(p).$$

활성화된 (M, t)가 성립하면, 전이 t를 발사하면 새로운 마킹 M'가 다음과 같이 정의된다:

$$M' = u_t \big( (M - I_t) + O_t \big).$$

We write  $M \xrightarrow{t} M'$  for one firing step and  $M_0 \xrightarrow{t_1 \cdots t_k} M_k$  for a finite firing sequence. The reachability set is

Reach

$$(N_A) = \{M \mid \exists \pi, M_0 \xrightarrow{\pi} M\}.$$

네트워크의 실용적 목적은 불가능한 호출을 거부하는 것뿐만 아니라.

네트워크는 *어떻게* 자원이 이동하는지, *어떤* 연산이 자원을 경쟁하는지, 그리고 *어떤* 이벤트가 인과적으로 독립적인지를 기록한다.

### 3.2 어댑터 스키마와 지역적 신뢰성 (Adapter Schema and Local Faithfulness)

Petri 네트는 추상적이지만, 테스트 오라클은 구체적인 Rust 실행을 대상으로 한다. 따라서 우리는 각 대상 라이브러리 도메인 d를 어댑터 스키마와 연결한다.

$$A_d = (\mathsf{Ctor}, \mathsf{Step}, \mathsf{Spawn}, \mathsf{Mark}, \mathsf{Assert}, \mathsf{Cleanup}, \Gamma, \rho_d).$$

여기서 Ctor는 초기 런타임 객체를 구성하고, Step은 모델링된 전이를 구체적인 Rust 연산으로 매핑하며, Spawn은 발생 가능한 이벤트 그룹을 태스크로 패키징하고, Mark는 이벤트 마커를 방출하며, Assert는 구체적인 검사를 인스턴스화하고, Cleanup은 정리(teardown)를 제한하며,  $\Gamma$ 는 구체적인 결과를  $\Omega$ 에 있는 관측 클래스에 매핑하고,  $\rho_d$ 는 구체적인 런타임 상태를 Petri-net 마킹으로 추상화한다.

우리는 구현과 모델 사이의 완전한 bisimulation을 요구하지 않는다.  
방법론적 요구사항은 모델링된 이벤트 경계에서의 *local faithfulness* 계약이다.  
이벤트 e가 $\eta(e)=t$인 경우, let

$$\operatorname{Step}_d(t, \sigma, \beta(e)) \rightsquigarrow (\sigma', o)$$

런타임 상태 $\sigma$ 에서 $\sigma'$ 로의 구체적 어댑터 스텝을 원시 관측 o와 함께 표시하고, $\Omega^{ok}_t, \Omega^{err}_t \subseteq \Omega$ 를 t의 모델링된 성공 및 오류 관측 클래스라고 하자. 합법적인 스텝에 대해 우리는 요구한다

$$\rho_d(\sigma) = M \land M \xrightarrow{t} M' \Longrightarrow \exists \sigma', o. \ \mathsf{Step}_d(t, \sigma, \beta(e)) \leadsto (\sigma', o)$$
$$\land \rho_d(\sigma') = M' \land \Gamma(o) \in \Omega_t^{ok}. $$

근접 법적 단계에서는 단일 전제 위반이 명시적 오류 클래스 결과에 매핑되도록 요구합니다:

$$\begin{split} \rho_d(\sigma) &= M \wedge |\Delta_F(M,t)| + |\Delta_G(M,t)| = 1 \\ &\Longrightarrow \exists \sigma', o. \ \mathsf{Step}_d(t,\sigma,\beta(e)) \leadsto (\sigma',o) \\ &\wedge \Gamma(o) \in \Omega_t^{err}. \end{split}$$

이 계약은 의도적으로 가볍습니다. 어댑터는 모델링된 단계와 경계 실패의 의미를 보존하도록 요구되며, 모든 내부 라이브러리 상태를 노출하거나 재구성할 필요는 없습니다.

### 3.3 재사용 가능한 전이 스키마 (Reusable Transition Schemas)

각 Petri net을 일회성 아티팩트로 만들지 않기 위해, 우리는 재사용 가능한 전이 스키마의 작은 라이브러리를 사용하여 동시 Rust API를 모델링합니다. 스키마는 튜플입니다

$$\theta = (P_{\theta}^{in}, P_{\theta}^{out}, g_{\theta}, u_{\theta}, \Omega_{\theta}),$$

타입이 지정된 입력 장소, 타입이 지정된 출력 장소, 가드, 토큰 업데이트 규칙, 그리고 단계에 부착된 관측 클래스들로 구성됩니다. 스키마를 인스턴스화하려면 심볼릭 장소 이름과 리소스 식별자를 바인딩하는 것만 필요합니다.

Four schemas are especially common in tokio::sync APIs:

\begin{split} &\theta_{\text{복제}}: \\ & \text{LiveHandle}(x) \rightarrow \text{LiveHandle}(x) + \text{LiveHandle}(x'), \\ &\theta_{\text{예약}}: \\ & \text{LiveSender}(s) + \text{Open}(c) + \text{Cap}(c, n) \\ & \rightarrow \text{LiveSender}(s) + \text{Permit}(s, c) + \text{Cap}(c, n-1), \\ &\theta_{\text{닫기}}: \\ & \text{LiveReceiver}(r) + \text{Open}(c) \rightarrow \text{LiveReceiver}(r) + \text{Closed}(c), \\ &\theta_{\text{소비}}: \\ & \text{LiveReceiver}(r) + \text{Buf}(c, n) \\ & \rightarrow \text{LiveReceiver}(r) + \text{Buf}(c, n-1) \\ & + \text{Obs}(\text{RecvOk}). \end{split}

보호자(guard)는  $\theta_{\rm reserve}$ 와  $\theta_{\rm consume}$ 에 대해 추가적으로 n>0을 요구한다. 근접-합법적 변이는 이러한 guard 또는 token 조건 중 정확히 하나를 위반함으로써 자연스럽게 발생한다. 예를 들어 채널이 닫혔거나 용량이 소진된 상태에서  $\theta_{\rm reserve}$ 를 시도하는 경우가 있다.

이러한 스키마는 대상 API 계열에 걸쳐 전이된다. mpsc에서는 $\theta_{\rm reserve}$ 모델이 획득을 허용한다; Semaphore에서는 동일한 스키마가 용량 토큰을 초과하는 획득을 모델링한다; watch에서는 $\theta_{\rm consume}$가 보이지 않는 업데이트의 관찰이 된다; 그리고 broadcast에서는 더 풍부한 결과 클래스 매핑을 가진 지연 민감 수신으로 변한다. 요점은 방법론적이다: Petri 모델은 각 호출 시퀀스마다 처음부터 수작업으로 작성되는 것이 아니라, 동시성 Rust 라이브러리 전반에 걸쳐 반복되는 자원-전이 관용구로부터 조립된다.

### 3.4 시나리오 의미 (Scenario Semantics)

추상 시나리오는 튜플이다

$$S = (E, \prec, \#, \eta, \beta, \Phi),$$

여기서 E는 유한한 이벤트 집합이며,  $\prec \subseteq E \times E$ 는 엄격한 부분 순서,  $\# \subseteq E \times E$ 는 대칭 충돌 관계,  $\eta : E \to T$ 는 이벤트를 Petri-네트 전이로 매핑하고,  $\beta$ 는 기호 자원과 페이로드를 이벤트 매개변수에 바인딩하며,  $\Phi$ 는 예상되는 결과 예측자와 전역 불변식을 포함한다.

A $\mathit{linearization}$ of $\mathcal S$는 $\mathit{E}$ 위의 $\prec$를 존중하는 모든 전단사 시퀀스이다. 우리는

$$Lin(S) = {\pi \mid \pi \text{ is a linearization of } (E, \prec)}.$$,

네트워크 $N_A$ 하에서 시나리오의 실행 가능 의미는

$$\operatorname{Exec}(\mathcal{S}, N_A) = \{ \pi \in \operatorname{Lin}(\mathcal{S}) \mid M_0 \xrightarrow{\eta(\pi)} M \text{ for some } M \},$$

여기서  $\eta(\pi)$ 는 이벤트에서 전이 시퀀스로  $\eta$  를 점별로 올린 것이다. 시나리오는  $\operatorname{Exec}(\mathcal{S},N_A)\neq\emptyset$  이면 합법적이다. 다시 말해, 적어도 하나의 선형화  $e_1,\ldots,e_n$ 이  $M_0\xrightarrow{\eta(e_1)\cdots\eta(e_n)}M_n$  을 만족한다.

경계 변형을 형식화하기 위해  $\Delta_F(M,t)=\{p\in P\mid I_t(p)\nsubseteq M(p)\}$  를 정의하고, t의 가드를  $g_t=q_1\land q_2\land\cdots\land q_r$  으로 쓴다고 가정한다.  $\Delta_G(M,t)=\{q_j\mid q_j(M)=\text{false},\ 1\leq j\leq r\}$  를 정의하면, 누락된 토큰과 위반된 원자 가드를 별도로 계산할 수 있다. 비활성 전이 t가 M에서 *근접 합법적* 이라면  $|\Delta_F(M,t)|+|\Delta_G(M,t)|=1$  이다. 이 정의는 우리가 원하는 특정한 의미적 경계 사례를 포착한다: 거의 활성화된 추적이지만 정확히 하나의 전제 조건만 위반하는 경우.

충돌 관계 # 은 토큰 클래스에 대해 경쟁하거나 같은 선형 자원을 사용하거나 사용자 선언된 경쟁 쌍에 해당하는 이벤트 쌍을 적대적으로 스케줄링해야 함을 기록한다. 부분 순서  $\prec$  는 필요한 인과 관계만을 기록하며, 완전히 확정된 스레드 스케줄은 아니다.

동시 시나리오에서는  $\Phi$  가 스케줄 단일값이 아니라 집합값이다. 비교 불가능한 이벤트가 경쟁할 수 있다면, 이벤트 e에 대한 허용되는 결과 클래스는 다음과 같을 수 있다

$$\Phi_e = \bigcup_{\pi \in \mathsf{Exec}(\mathcal{S}, N_A)} \Phi_e^\pi,$$

여기서  $\Phi_e^{\pi}$  는 선형화  $\pi$  에서 e의 모델링된 관측 클래스이다. 이는 오라클이 다중 경쟁 허용 결과를 수용하면서도 어떤 합법적 선형화도 허용하지 않는 클래스를 거부하도록 한다.

### 4.1 세 가지 시나리오 패밀리 (Three Scenario Families)

이들은 단순히 긴 추적이 아니라 의미적으로 드문 마킹에 도달하도록 선택된 완전히 활성화된 추적이다. 우리는 휴리스틱 점수를 부여한다

깊이

$$(\pi) = \alpha U(M_k) + \beta C(\pi) + \gamma X(\pi),$$

### 4.2 생성 알고리즘

알고리즘 1은 의도적으로 모델 중심적입니다. 다음에 어떤 이벤트가 발생해야 할지는 코드 생성 편의성보다 도달 가능성과 충돌 구조에 의해 결정됩니다.

실제로 근접 합법 변이는 균일하게 삽입되지 않습니다. 합법 접두사가 마킹 M에 도달한 뒤, 우리는 후보 경계 이벤트를 다음과 같이 점수화합니다

MutScore(M, t) = w_1 \mathbb{1}[|\Delta_F(M, t)| + |\Delta_G(M, t)| = \mathbb{1}]
+ w_2 \text{Stale}(M, t) + w_3 \text{ConflictCtx}(M, t),

여기서 Stale은 최근에 무효화된 리소스를 재사용하는 작업에 보상을 주고, ConflictCtx는 높은 충돌 프런티어 근처에 배치된 변이에 보상을 줍니다. 이는 동시성 라이브러리에서 흔히 잘못 처리되는 경계 오류 유형에 예산을 집중합니다.

## 5 LLM 구체화

### 5.1 프롬프트 계약

LLM은 시나리오 튜플과 API 어댑터 스키마에서 조합된 형식화된 프롬프트를 받습니다:

```
P(S, A_d) = (Hdr, Res, Ev, Ord, Conf, Obs, Out, Ban).
```

이 필드들은 리소스 선언, 타입이 지정된 이벤트, 순서 엣지, 동시성 힌트, 예상 관측 클래스, 그리고 가상 세미틱 이벤트나 약화된 어서션과 같은 금지된 동작을 인코딩합니다. 대표적인 프롬프트 조각은 Listing 2에 표시됩니다.

  - Rust 테스트 코드만 반환한다

LLM 출력은 $Y = (c, \mu, a)$로 표현되며, 여기서 c는 Rust 테스트 코드, $\mu$는 시나리오 이벤트를 실행 시점 마커에 매핑하고, a는 생성된 어서션 집합입니다.

우리는 생성된 아티팩트를 실행에 사용하기 위해서는

\begin{aligned} \mathsf{잘 형성된 (WellFormed)}(Y,\mathcal{S}) &\iff \mathsf{컴파일 (Compiles)}(c) \\ & \wedge \forall e \in E, \ \mu(e) \downarrow \\ & \wedge \mathsf{발명된이벤트없음 (NoInventedEvents)}(Y,E). \end{aligned}

이것은 정적 입학 필터이며, 구조적 오라클은 나중에 런타임 트레이스가 실제로 의도된 부분 순서를 준수하는지 확인한다.

평가를 위해 우리는 부분 구조적 충실도 점수를 사용한다. $h^*$ 를 시나리오 이벤트와 방출된 마커 사이의 최대 카드인수 순서 보존 부분 매칭이라고 하자. 우리는 정의한다

$$\operatorname{Fid}(\mathcal{S}, \tau) = \frac{|\operatorname{dom}(h^{\star})|}{|E|}.$$

이것은 도구가 전체 구조적 오라클이 실패하더라도 의도된 구조가 얼마나 구체화에 살아남는지 측정할 수 있게 한다. 핵심 규칙은 LLM이 구문, 헬퍼 이름, 로컬 스캐폴딩을 선택할 수 있지만 새로운 의미 이벤트를 발명하거나 순서 제약을 완화하거나 예상되는 결과 클래스들을 재정의할 수 없다는 것이다.

### 5.2 구체화 및 수리 루프

우리는 생성된 테스트가 컴파일되고 런타임 오라클에 필요한 마커 구조를 노출하도록 요구한다. 알고리즘 2는 루프를 제공한다. 이 루프는 의도적으로 엄격한데, 성공적인 컴파일만으로는 시나리오가 올바르게 구체화되었음을 증명하기에 충분하지 않기 때문이다.

## 6 페트리-가이드 스케줄 탐색

시나리오 튜플은 이미 어떤 이벤트가 인과적으로 제약을 받고 있고 어떤 쌍이 의미상 충돌하는지를 알려준다. 우리는 이 정보를 사용해 스케줄 탐색을 형성하고, 모든 하니스 변형을 동일하게 중요하게 여기지 않는다.

부분 순서 시나리오는 또한 작업 스켈레톤을 유도한다

$$K_S = (V_{\text{task}}, E_{\text{spawn}}, E_{\text{conf}}),$$

여기서 $V_{\text{task}$는 작업 소유권에 따라 이벤트를 분할하고, $E_{\text{spawn}$는 스폰-부모 관계를 기록하며, 그리고

$$E_{\text{conf}} = \{(e_i, e_j) \mid e_i \parallel e_j \land (e_i, e_j) \in \#\}$$

비교 가능한 충돌 쌍을 수집한다. 구체적인 하니스 변형은 $E_{\rm conf}$의 선택된 쌍 주위에서 작업 생성 순서, 장벽 배치, 명시적 yield 포인트를 선택한다.

이 신호를 사용하기 위해 Loom 내부를 수정할 필요가 없다. 대신, 우리는 서로 다른 고충돌 프론티어 선택을 우선시하는 작은 집합의 *스케줄-형성 하니스 변형*을 생성하고, Loom-호환 하니스가 존재할 때마다 각 변형을 Loom에서 실행한다. 직접 Loom 통합이 불가능한 API의 경우, 동일한 스케줄-형성 변형을 결정론적 스케줄러 래퍼에서 실행할 수 있다. 따라서 개선은 Loom 내부가 아니라 Loom 위에서 이루어지며, 페트리 네트워크가 어떤 동시성 스켈레톤이 스케줄 예산을 받을 자격이 있는지를 선택한다.

YieldPts(h)는 하니스 변형 h가 장벽이나 yield를 통해 명시적으로 노출하는 충돌 쌍을 나타내며, $C_{j-1}$는 이전 변형에 의해 이미 커버된 집합이다. 따라서 우리는 미커버된 충돌 이득에 따라 후보 변형을 순위화할 수 있다:

$$h_j = \arg \max_{h \in \mathcal{H}(\mathcal{S})} \sum_{(e,e') \in \mathsf{YieldPts}(h) \setminus C_{j-1}} w(e,e').$$

이것은 단순 스케줄 열거보다 구체적인 방법론적 개선을 제공한다: Loom은 여전히 각 하니스 내에서 스케줄을 탐색하지만, Petri 레이어는 의미론적으로 의미 있는 충돌 커버리지를 최대화함으로써 스케줄 예산을 받을 하니스를 결정한다.

평가 대상은 용량이 한 개인 제한된 Tokio MPSC 채널이다. 검토된 시나리오는 일곱 개의 이벤트를 포함하며 정확히 두 개의 합법적인 선형화가 있다:

### 8.2 RQ1: 아티팩트 제약 프롬프트가 실행 가능한 Tokio 코드를 생성할 수 있는가? (Can the artifact-constrained prompt produce executable Tokio code?)

생성된 테스트는 기록된 툴체인에서 컴파일되고, 일반 평가기에서 완전히 실행된다. 이는 파이프라인의 첫 번째 요구 사항이다: 프롬프트와 생성 계약이 실제 Tokio 테스트를 생성할 만큼 강력해야 하며, 스케치나 의사코드 조각이 아니라 실제 테스트를 만들어야 한다.

같은 소스는 시나리오 라벨, 예상 관측값, 그리고 평가기가 소비하는 런타임 증거 포인트도 함께 포함한다. 이 MPSC 예제에서는 이러한 요소들이 평가 크레이트에 MPSC-특정 검사기가 없더라도 세 번의 성공적인 실행을 얻기에 충분했다.

### 8.3 RQ2: 생성된 러너가 스케줄 민감 구조를 보존하는가? (Does the generated runner preserve schedule-sensitive structure?)

시나리오는 e3과 e4의 상대적 순서에 따라 두 개의 합법적인 선형화를 구분하며, 러너는 런타임 트레이스에서 그 구분을 보존한다. 각 실행은 동일한 14개의 레코드를 방출하며, 두 스케줄에 고르게 분배된다. 평가기는 관측된 레코드 순서가 아티팩트 오라클과 일치함을 확인한다.

이것이 중요한 이유는 예제가 단순히 '통과하는 테스트'가 아니라, 최종 트레이스에 합법적인 순서가 남아 있는 작은 스케줄 패밀리이기 때문이다. 바로 프로토타입이 보존하려는 구체적인 구조적 특성이다.

### 8.4 RQ3: 피드백 수리로 구체적인 불일치를 시나리오를 변경하지 않고 복구할 수 있는가? (Can feedback repair recover from a concrete mismatch without changing the scenario?)

이것이 현재 프로토타입에 적합한 수리 형태이다: 생성된 코드는 표면 구문과 증거 파이프라인을 변경할 수 있지만, 모델링된 시나리오를 조용히 변경하거나 오라클을 약화시켜서는 안 된다.

### 8.5 RQ4: 아티팩트 경계가 일반 파이프라인을 주제별 모델에서 충분히 분리하는가? (Is the artifact boundary strict enough to isolate the generic pipeline from the subject-specific model?)

일반 LLM 및 평가기 층은 손으로 작성된 MPSC 논리가 아니라 휴대 가능한 아티팩트를 소비한다. 주제별 의미는 패밀리 크레이트에 존재한다: 검토된 CPN, 검토된 시나리오, 런타임 관측 계약. 일반 파이프라인은 이후 생성된 소스를 컴파일하고 실행하며, 방출된 JSONL 레코드를 아티팩트에서 파생된 오라클과 비교한다.

제한점은 범위이다. 이는 아직 한 개의 실행 예제에 대한 예비 평가이며, 대규모 변이 연구나 스케줄 예산 벤치마크가 아니다. 결과는 통계적 우월성이라기보다 실현 가능성을 뒷받침한다.

### 8.6 유효성에 대한 위협 (Threats to Validity)

주요 위협은 규모이다. 현재 평가에서는 한 개의 검토된 MPSC 주제와 한 개의 수정된 생성 러너만을 다룬다. 변이 코퍼스, 순수 프롬프트 기준선, 또는 스케줄 탐색 비교는 아직 포함되지 않았다. 그럼에도 불구하고, 제공된 증거는 완성된 벤치마크라기보다 작동하는 프로토타입과 검증된 아티팩트 경계를 주장하는 arXiv 제출에 충분하다.

Petri 네트워크는 상태 기반 시스템에서 형식적 모델링, 도달 가능성 추론, 테스트 도출에 오랫동안 사용되어 왔습니다 [&#91;4,](#page-8-4) [5&#93;](#page-8-5). 이 연구 라인은 토큰 기반 모델이 왜 유용한지를 보여줍니다: 토큰 기반 모델은 평면 상태 머신보다 다중성, 인과성, 충돌을 보다 자연스럽게 표현합니다. 우리의 설정은 누락된 구체화 문제를 추가합니다. 출력은 추상 트레이스로 멈추지 않아야 하며, 작업, 소유권 이동, 시간 한계 및 실행 가능한 어설션을 포함한 컴파일 가능한 Rust 테스트가 되어야 합니다. 따라서 SyncPetri는 Petri 네트워크를 전체 테스트 엔진이 아니라 의미론적 중간 표현으로 사용합니다.

상태 기반 API 테스트와 깊은 상태 탐색. REST-ler는 의존성 인식 생성이 상태 기반 API에 필요함을 보여 주었습니다. 순진한 요청 조합은 의미 있는 깊은 상태에 거의 도달하지 못하기 때문입니다 [&#91;1&#93;](#page-8-6). StateAFL 및 이후의 상태 기반 그레이박스 작업 역시 실패가 종종 시스템이 의미론적으로 구분되는 상태에 진입한 후에만 발생한다고 주장합니다 [&#91;2,](#page-8-7) [6&#93;](#page-8-8). 우리는 그 동기를 공유하지만, 대상과 추상화는 다릅니다. 그 시스템들은 네트워크 또는 프로토콜 인터페이스에 초점을 맞추는 반면, SyncPetri는 리소스 소유권, 핸들 무효화, 예약된 기능, 스케줄 민감한 부분 순서에 따라 하드 행동이 달라지는 인-프로세스 Rust 라이브러리 API를 대상으로 합니다. 우리의 근접-합법 시나리오 또한 무작위의 잘못된 입력이 아니라 모델에 의해 정의된 의미론적 경계에 목표를 둡니다.

LLM 기반 테스트 생성. TitanFuzz와 Fuzz4All은 수동 생성기가 비용이 많이 드는 도메인에서 LLM이 다양한 테스트와 프로그램을 생성할 수 있음을 보여 주었습니다 [&#91;3,](#page-8-9) [13&#93;](#page-8-10). CoverUp는 강력한 모델에서도 외부 피드백과 구조가 여전히 중요함을 추가로 보여 주었습니다 [&#91;7&#93;](#page-8-11). SyncPetri는 그 교훈을 채택하지만 가이드 신호를 바꿉니다. 개방형 프롬프트나 커버리지에만 의존하는 대신, 우리는 리소스 바인딩, 순서 제약, 허용 가능한 결과 클래스, 금지된 의미론적 편집을 포함한 타입이 지정된 이벤트 그래프를 제공하고, 구조적 오라클로 결과를 판단합니다. 따라서 기여는 단순히 LLM을 테스트에 사용하는 것이 아니라, LLM을 코드 구현에 제한하면서 의미론적 의도를 모델 외부에 두는 것입니다.

체계적인 동시성 탐색. Loom은 Rust 동시 코드에 대한 제어된 스케줄 탐색을 제공합니다 [&#91;8&#93;](#page-8-12). 우리의 작업은 경쟁이 아니라 보완적입니다. Loom은 하니스 내부에서 마이크로 인터리빙을 탐색하는 반면, SyncPetri는 리소스 모델에서 레이스 윈도우와 충돌 쌍을 추출하여 그 하니스를 처음부터 의미론적으로 의미 있게 만들려고 합니다. 따라서 스케줄쉐이핑 구성요소는 스케줄러 위에서 작동합니다: 탐색 예산을 받을 가치가 있는 동시성 골격을 우선순위화하지만, 스케줄러 내부 검색 알고리즘을 수정하지는 않습니다.

위치 지정. 이들 연구 라인 전반에 걸쳐, 누락된 조합은 리소스 인식 동시성 의미론에서 실행 가능한 Rust 테스트로 이어지는 모델 기반 경로이며, 의미론적 오라클을 LLM에 위임하지 않는 것입니다. SyncPetri는 Petrinet 시나리오 합성, 제약 구체화, 스케줄 인식 하니스 구성, 그리고 계층적 런타임 판단을 하나의 테스트 워크플로우에 결합함으로써 그 공간을 차지합니다.

## 10 결론 (Conclusion)

본 논문은 동시적 상태를 가진 Rust API에 대한 LLM 기반 테스트 생성을 위한 Petri 네트 제약 아키텍처인 SyncPetri를 제시한다. 주요 논제는 모델 구조가 의미론, 경계 변이, 그리고 동시성 노출을 제어해야 하며, LLM은 실행 가능한 구현만을 제어해야 한다는 것이다. 이 논제를 뒷받침하기 위해 우리는 대상 도메인을 형식화하고, 시나리오 언어를 정의하며, 구체화 및 수리 루프를 명시하고, Petri 가이드 스케줄 형성을 제안하고, 다층 의미론 오라클을 도입하였다. 이 모든 요소가 결합되어 주요 트랙 규모의 방법론을 형성한다: Petri 네트와 LLM이 결합될 수 있다는 단순한 스케치가 아니라, 테스트 생성 시스템에서 어떻게 결합되어야 하는지에 대한 구체적인 설계이다.
